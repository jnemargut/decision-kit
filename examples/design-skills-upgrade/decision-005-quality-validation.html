Decision 5 of 6 · Verification

How do we know the designs actually got better?

"Looks better to me today" is how design skills quietly regress. This decision picks the verification mechanism — both for proving this upgrade worked and for keeping quality from sliding as the kit takes contributions.

Builds on Decisions 1–4: the upgrades produce enforceable claims — ban-list compliance, one rule-breaking move per tension, signal traceability, composition variety. Those claims are checkable; the question is where and how.
Research Context
  • Agents that look at their own output converge in 2–3 iterations instead of 10+. The Playwright-screenshot feedback pattern ("Eyes" skill, Playwright MCP workflows) is the documented quality multiplier for AI-generated UI: render, inspect, fix what you can see. luca-becker.me, azukiazusa.dev, mcpmarket "Eyes"
  • Analytic, binary rubrics beat numeric scales for LLM judging. "Binary or low-precision scoring produces more reliable results than high-precision numerical scales"; criterion-by-criterion rubrics "reveal why a system failed." Don't ask a judge for 7.5/10 aesthetics — ask "is any banned font present: yes/no," "would you mistake this for the previous output: yes/no." Adnan Masood (rubric evals), Evidently AI, Confident AI
  • Pairwise A/B judging is the standard for regression. LLM-as-judge "works well even when scoring rubrics are subjective" and is most reliable comparing two outputs side-by-side — exactly the before/after shape of this upgrade. LangChain, Langfuse eval guides
  • Several of the new claims need no model judgment at all. Ban-list compliance (grep the CSS for Inter/Roboto), font-overlap-across-traditions (count shared families), WCAG contrast (compute it) are deterministic script checks — free, instant, CI-able.
  • Constraint: screenshots need tooling the kit doesn't currently require. Headless Chrome ships on most dev Macs (chrome --headless --screenshot), and Claude Code reads images natively — but the kit is pure-prompt today. Any screenshot step needs a graceful no-tooling fallback (HTML/CSS self-review).
Options
★ Recommended
A

Runtime critique gate — give the skills eyes

Both skills end every run with: deterministic checks (ban list, contrast) → screenshot via headless Chrome if available → analytic binary self-critique (hierarchy, density, distinctiveness, signal traceability) → fix and re-check, max 2 loops. Falls back to CSS-level self-review when no browser tooling exists.

1Generate styled output / showcase
2Script checks: bans, contrast, font overlap — fail fast
3Screenshot → binary rubric critique (or CSS review fallback)
4Fix findings, re-check once, then ship to user

Improves every future run for every user — validation becomes a product feature

Completes the arc: D1 fixed the pool, this adds the eyes

Graceful degradation keeps the kit's no-dependency promise

Adds ~30–60s per run; rubric needs tuning to avoid nitpick loops

Validates runs, not the upgrade itself — needs a small before/after sample for the PR

B

Golden gallery regression suite

A fixed test matrix — 5 artifact types × 6 traditions, 3 workshop profiles — regenerated before/after any change, rendered into a side-by-side gallery page. Human taste is the judge.

1Freeze test inputs in examples/
2Regenerate matrix on each change
3Gallery HTML: old vs new, side by side
4You eyeball; PR links the gallery

Human taste stays the arbiter — most trustworthy verdict

Gallery doubles as repo showcase/docs material

Manual: regenerating a 30+ cell matrix per change costs real time/tokens

Catches regressions only when you remember to run it

C

LLM-judge eval harness

An offline eval: analytic binary rubric + pairwise old-vs-new judging across the test matrix, scores tracked per version. The kit gets a real evals story.

1Define binary criteria per claim (D1–D3)
2Judge model scores matrix outputs pairwise
3Score deltas gate the release

Quantified, repeatable, contributor-proof

Research-backed shape: binary + pairwise is where judges are reliable

Real harness infra — new territory for a pure-prompt repo

Judge shares the generator's biases; can bless samey-but-tidy output

D

Sameness metric

Measure convergence directly: generate N outputs from N different inputs, compute font/palette overlap, then a matching test — can a judge tell which input produced which output? Upgrade passes only if distinguishability jumps.

1N diverse inputs → N outputs
2Overlap stats: fonts, palettes, layout
3Judge matching test (input ↔ output)
4Distinguishability score per version

Measures the exact complaint — sameness — not proxies

The matching test is clever evidence for the PR story

Measures variety, not quality — N distinct ugly outputs pass

Most build effort for the narrowest signal

Recommendation: A, with a slim slice of B riding along: the runtime gate is the only option that makes every user's output better instead of just auditing yours — and a small before/after gallery (one artifact × 4 traditions, 1 workshop profile) is cheap to produce as the PR's evidence.
