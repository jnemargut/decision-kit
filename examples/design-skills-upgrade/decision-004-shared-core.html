Decision 4 of 6 · Architecture

Where does the shared design DNA live?

Decisions 1–3 created shared assets: the banned-defaults list, the characterful font pool, palette principles, composition signatures, and amplification rules. Both skills need them. The architecture question: one source of truth, or self-contained copies?

Builds on Decisions 1–3: ban list + font pool (D1), composition signatures (D2), and amplification rules (D3) are the assets whose home this decision picks.
Research Context
  • Skills are designed to be self-contained directories. The canonical structure is SKILL.md + scripts/ + references/ + assets/; cross-skill paths are not part of the model, and configuration "is not loaded from additional directories." A skill that reads a sibling folder breaks when installed alone. Claude Code skills docs, skill-development SKILL.md
  • SKILL.md should be ~1,500–2,000 words with detail pushed to references/. Audit: your visual-design SKILL.md is ~1,800 lines (the entire 30-tradition library is inline). It needs the references/ refactor regardless of this decision — which makes "where does the library file live" the live question. Anthropic skill-building guide, leehanchung deep dive
  • Progressive disclosure is the documented pattern. Frontmatter → SKILL.md → referenced files loaded only when needed. A traditions library as a references/ file is cheaper on context than inline, and only loads for the steps that need it. Claude Code docs
  • Plugins exist for exactly this bundling problem. A .claude-plugin/plugin.json can ship multiple skills with shared assets under one install, namespaced. Decision-kit currently distributes skills as copy-in folders — a plugin packaging would change the constraint, but that's a distribution shift for the whole kit, not just these two skills. Claude Code plugin docs
  • Drift is the real cost of duplication. The kit already shows it: visual-design and design-system each carry their own partial font opinions today, and they disagree. Two copies of a 30-tradition library will diverge within months of accepting outside PRs.
Options
A

Duplicate into each skill

Copy the ban list, font pool, and shared principles into each skill's references/ folder. Each skill fully self-contained, no tooling.

thinking/visual-design/ ├── SKILL.md └── references/ ├── design-dna.md (copy 1) └── traditions.md thinking/design-system/ ├── SKILL.md └── references/ └── design-dna.md (copy 2)

Zero tooling, matches how skills install today

Contributors edit one skill without understanding the other

Copies diverge — the kit's own history proves it

Every DNA improvement is a two-file PR that reviewers must diff-match

★ Recommended
B

Single source, synced at release

One canonical shared/design-dna/ in the repo. A tiny sync script (or checklist step) copies it into each skill's references/ before release. Installed skills stay fully self-contained.

shared/design-dna/ ← edit here only ├── banned-defaults.md ├── font-pool.md ├── traditions.md └── composition-signatures.md thinking/visual-design/references/ ← generated thinking/design-system/references/ ← generated scripts/sync-dna.sh

One source of truth; installed skills still self-contained

Forces the overdue SKILL.md → references/ refactor

Future skills (showcase art direction, others) adopt the DNA by adding one sync target

A sync step contributors must know about (CI check mitigates)

Generated files in-repo can confuse first-time PR authors

C

Runtime shared directory

Skills read ../design-dna/ at runtime. True single file at install too — but only if users install the whole kit in the expected layout.

~/.claude/skills/ ├── design-dna/ ← one copy ever ├── visual-design/ │ └── SKILL.md reads ../design-dna/ └── design-system/ └── SKILL.md reads ../design-dna/

No sync step, no duplication anywhere

Breaks standalone installs — the unsupported pattern per docs

Silent degradation: skill runs but without the DNA if path missing

Couples every user's install layout to the repo's structure

D

Extract a third skill: /design-dna

The shared core becomes its own user-facing skill — browse traditions, view the ban list, manage project aesthetic memory — and the other two treat it as the library owner.

thinking/design-dna/ ← new skill ├── SKILL.md (browse/curate) └── references/ └── (the library) visual-design ──reads──▶ design-dna design-system ──reads──▶ design-dna

The library becomes a product surface, not just plumbing

Clean conceptual home for project aesthetic memory

Inherits C's path coupling problem for the cross-reads

Third skill to document, maintain, and explain — scope growth this project doesn't need yet

Recommendation: B. It's the only option that gets single-source maintenance AND keeps installed skills self-contained — and it forces the references/ refactor your 1,800-line SKILL.md needs anyway.
