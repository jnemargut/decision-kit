How does this land in decision-kit?

It's your repo — but it has a public CONTRIBUTING.md, a spec, and the ambition to take outside contributors. How this work lands sets the precedent for every future contribution. Four shapes for the same payload.

The payload (Decisions 1–5): shared/design-dna + sync script, /visual-design overhaul + composition signatures, /design-system amplification rules, runtime critique gate, before/after gallery evidence.
Research Context
  • Your own CONTRIBUTING.md already votes. It asks for "one PR focused on a single change," an issue first for anything non-trivial, end-to-end testing on real examples — and that significant proposals include the resulting .decisions/ folders in the PR. This strategy run is itself that artifact. decision-kit CONTRIBUTING.md
  • Review effectiveness collapses past ~400 lines. The Cisco study: defect detection drops sharply beyond 400 LOC per review. The full payload here is thousands of lines across 6+ files — un-reviewable as one unit, even by you-plus-ultrareview. Knack engineering, awesomecodereviews.com
  • Stacked/sequential PRs keep the author unblocked. Each phase merges as it's ready while the next is in flight; "teams naturally break work into 5–10 smaller PRs" and get faster review and higher quality on both sides. Ben Congdon, Axolo
  • The repo discourages variant forks and rewards composition. "Propose tweaks to existing skills" over new near-duplicates — which supports upgrading the two skills in place rather than shipping a v2 fork beside them. decision-kit CONTRIBUTING.md
  • Dependency order is real. D4's shared/design-dna must exist before either skill can reference it; the critique gate (D5) touches both skills and lands cleanest last. The payload has a natural 4-phase topology.
